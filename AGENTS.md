# TrackHarbor Agent Instructions

## Project Goal

The core goal is to synchronize and store collections of tracks, then download
them for local use. The primary use case is keeping local copies of Spotify
playlists or YouTube video/audio without requiring a subscription.

## Current focus: deslop

The current priority is **deslop**: reviewing all features added or generated by
AI, understanding how they actually work, and standardizing their implementation.
Prefer improving existing functionality over adding new features unless the user
explicitly requests them.

1. **Understand first.** Trace the existing behavior, data flow, dependencies,
   and purpose before proposing changes. Do not rewrite code you have not understood.
2. **Review and standardize.** Check AI-generated features against the intended
   workflow. Fix defects and unnecessary complexity; bring naming, structure,
   interfaces, error handling, and UI patterns into line with project conventions.
   Preserve intentional behavior and keep each change focused.
3. **Preview design changes first.** Create separate temporary HTML previews and
   show them to the user before changing the application UI. Follow
   `.agents/skills/design/SKILL.md`, including both themes and responsive layouts. Delete
   the previews after review and implementation; do not commit preview artifacts.

## Project boundaries

- The server is the only supported application. Its Go module, command,
  configuration, database, and source integrations live at the repository root.
  The old CLI is archived in `.deprecated/cli/` and is not maintained or built.
  Never point the server at the CLI's `~/.trackharbor/vault.db`.
- The web UI has no user login yet: bind it to loopback by default and do not
  expose it publicly without access control. Multi-device access needs login.

## Development

- Before adding or changing application settings, load
  `.agents/skills/settings/SKILL.md`. Store all new settings in the database
  `settings` table, never in `config.yaml` or `internal/config.Config`.
- Before changing the server web UI's visual elements, load the project `design`
  skill at `.agents/skills/design/SKILL.md` and follow its element tokens and light/dark theme
  requirements for every new or changed element. The HTML-preview workflow above
  is mandatory for design changes and is an explicit exception to the no-drafts
  rule below.
- Always import UI icons from `@hugeicons/core-free-icons`; never draw or copy
  SVG paths, icon data arrays, or Unicode substitutes into templates, scripts,
  styles, or previews. Add named imports to `scripts/build-icons.mjs` and run
  `npm run icons:build`. `internal/web/assets/icons.svg` is generated output:
  commit it, but never edit it by hand. Render icons through the shared `icon`
  template or references to this generated sprite. Keep the approved custom
  CSS brand mark; it is branding, not a library action icon.
- Prioritize the core workflow over speculative features, but keep application
  boundaries explicit and deployment/security constraints visible.
- When a request is clear, proceed directly to implementation. Do not create
  preliminary drafts, specifications, design documents, or implementation plans
  unless explicitly requested. Do not require separate approval of such documents.
- If a plan is requested or needed, present it in the conversation only.
  Do not save plans in `docs/` or any other project file.
- Do not write or run tests, including unit, integration, race, and live tests,
  unless explicitly requested. Do not delete existing tests.
- Do not update README files unless explicitly requested by the user.
- Keep changes small, simple, and focused on the task. Follow the existing code
  structure and style; avoid unnecessary abstractions and unrelated refactoring.
- Never delete or edit existing database migrations. If a migration is wrong,
  correct or reverse it with a new migration instead.
- Report errors with clear explanations so problems can be fixed quickly and
  development can continue.
- Server logs use the shared global zap logger in `internal/logging`, with
  readable text output to `logs/YYYY-MM-DD.log` and colored text to stderr.
  Select the file by the current local calendar date on every write, not the
  startup date; append on restart and never put ANSI colors in log files.
  Info is the default minimum level. Never add Debug log statements: if an event
  does not belong in Info (or Warn/Error), do not log it. Keep polling, transfer
  progress, and other noisy events out of logs. Never log credentials, tokens,
  proxy URLs, request or response bodies, or upstream errors that may contain secrets.
- Keep final responses concise and describe what changed. Do not claim that code
  was verified or tests passed when those checks were not performed.

These project rules take precedence over default planning and test-driven
development workflows unless explicitly updated by the user.

## Commits

- For deslop fixes and standardization, use exactly `deslop: <message>`.
  This is an exception to Conventional Commits: do not add a component scope or
  wrap it in another prefix such as `fix(server): deslop: ...`.
- For other changes, use Conventional Commits with a required component scope:
  `type(component): message`. Choose the component affected by the change,
  such as `server`, `cli`, or `common` for shared code. Examples:
  `feat(server): add top-bar`, `feat(common): better proxy logic`,
  `fix(vk): skip tracks without audio URLs`. See `CONTRIBUTING.md`.
- When asked to create a commit, keep the human as the primary author and add
  the assistant as a co-author using a `Co-authored-by:` commit-message trailer.
